## 一、方案拆解：三端一体

参赛方案《芯宿·智控》是一条 **「自助入住一体机 — 智能门锁 — 语音控制机器人」** 的三端闭环，主控统一为 K1。按可交付性拆成四块：

| 编号 | 终端 / 能力 | 依赖硬件 | 现在能否做 |

| ① | 自助入住一体机（身份核验→选房→支付→发卡→门锁授权） | 身份证读卡器、摄像头、二维码识别器、RFID、触摸屏、音响 | **能，本次已完成**（门锁用模拟层） |

| ④ | 边缘网关（设备编排、审计、看板） | 仅 K1 | **已完成**（REST + SSE + SQLite） |

方案 PPT 里三个终端共用一套网关编排，本次把 **网关 + 一体机** 做成可运行实体，门锁与机器人留标准插槽。

## 三、本次已完成（可现场演示）

### 1. 自助入住一体机 · 全流程（①）

`待机 → 刷身份证 → 人脸采集 → 选房 → 扫码支付 → 写入房卡 → 下发门锁 → 完成`

- 800×480 全屏触摸 kiosk（Chromium kiosk + 自研前端，固定 800×480 舞台自适应缩放）
- 每一步都有 **TTS 语音引导**（离线 espeak-ng，48kHz，预生成语音包，断网可用）
- 每一步都有 **真实外设接入点**，插上即用，不插走模拟按钮（界面上明确标注"演示"）
- 入住结果落 SQLite，含证件、房号、金额、房卡 UID、临时开门码、时间戳
- 完成页展示「房号 / 临时开门码 / 房卡 UID / 门锁状态」，60 秒无操作自动回待机

### 2. 身份核验（身份证读卡器）

读卡器厂商 SDK 多为 Windows DLL 或私有 HID 协议，**不在驱动层硬啃**，而是做成标准桥接口：

- 桥接进程把证件 JSON 写到 `/run/zhikong/idcard.json`，或 `POST /api/idcard/inject`
- 业务层立即收到一次"刷卡"，**换任何品牌读卡器只改桥接脚本，一体机零改动**
- 现在用内置模拟证件（陈思远 / 李梦琪 / 王浩然）跑通流程

### 3. 二维码识别器 + RFID 读卡器（HID 抓取）

这两类设备在 Linux 下几乎都是 **USB HID 键盘**（扫完自动回车）。本系统用 evdev 裸事件读取 + `EVIOCGRAB` 独占：

- 自动发现键盘型设备，按名称/VID 归类为 `qr` 或 `rfid`
- 字符流按「回车 / 350ms 静默」聚合成一次完整扫描
- **独占设备**，扫码内容不会漏进浏览器输入框
- 当前步骤决定路由：支付步骤的码 → 付款码；发卡步骤的码 → 房卡 UID
- 现场插入新设备后，用 `selftest.py --hid 20` 打印设备名与扫描内容，把名称加入 `config.json` 即自动识别

### 4. 摄像头（人脸采集）

- 自动遍历 `/dev/video*`，排除 `vivi`/`mvx`/解码节点，逐节点试开并取帧
- 取到帧即采用，兼容 UVC USB 摄像头与 CSI sensor（若接了 sensor）
- 前端在「人脸」步骤才拉 MJPEG 流（避免页面常驻占用），无设备时优雅降级为占位图
- 抓拍存 `/opt/zhikong/data/photos/face_*.jpg`，随订单归档
- ⚠️ 当前无摄像头，人脸比对为**模拟通过**；接入后是真实抓拍 + 预留比对接口

### 5. 语音服务（③ 的服务派单部分）

- 端侧关键词意图路由（灯光 / 空调 / 窗帘 / 服务 / 查询 五类），不依赖云端
- 说"送一双拖鞋" → 生成工单（房号+物品+状态）→ 前台可取单
- 说"几点退房" → 本地知识库应答（退房时间 / 早餐 / WiFi / 停车）
- 回复同步 TTS 播报 + 界面气泡
- ⚠️ ASR（语音转文字）尚未接入，目前用**快捷指令 + 文本输入**触发；接口 `POST /api/voice {text}` 已固定，接 ASR 后只需把识别文本灌进来

### 6. 边缘网关（④）

- 纯标准库 HTTP 服务（riscv64 无编译依赖），REST + SSE 实时推送
- 设备注册表：每 2 秒扫描 USB / 输入设备 / 视频节点 / 声卡 / 串口，变化即推送前端
- SQLite 三张表：`orders`（入住）、`workorders`（服务工单）、`audit`（全链路审计）
- systemd 常驻，崩溃 3 秒自愈，开机自启

## 四、为什么这么切分（工程判断）

1. **不让外设缺失阻塞软件进度**
   K1 上四个 USB 外设全空，如果等硬件齐了再写，今天什么都交付不了。做法是「接口先行 + 降级可演示 + 插上即真」，硬件到位时不需要改业务代码。

2. **不赌读卡器协议**
   二代身份证读卡器是**唯一有真实风险**的外设（SAM 安全模块 + 厂商私有协议，Linux 支持参差）。因此把它隔离成"桥接进程写 JSON"，而不是让它卡住主流程。哪怕明天协议还没通，演示也不受影响。

3. **门锁按"协议先定"推进**
   门锁板下午到，但门锁协议（下发凭证 / 开门 / 心跳）今天先定死并实现三种传输（mock / 串口 / HTTP），板子到了只做**同一份 JSON 的收发**，联调时间从"半天"压到"一小时"。

4. **语音先做"能干活"的部分**
   ASR 在 riscv64 上是重活（无成熟 wheel，需自编译 whisper.cpp 或等 sherpa-onnx）。先把 **意图理解 + 工单 + TTS 播报** 做完——这部分才是业务价值所在，ASR 只是输入方式，可后补。

### 7.2 二维码识别器：✅ 已打通

- 后端 evdev 独占抓取成功：`[hid] capture USBScn Chip USBScn Module (qr) grabbed=True`
- **现场真实扫码验证**：扫到 EAN-13 `BARCODE0001`，已写入 `audit(scan)` 并在界面顶部弹出「已识别 条码 …」
- 关键修复：`config.json` 的 `scanner_name_re` 之前没被 `ScannerHub` 使用，已接通

### 7.3 二代身份证读卡器：⚠️ 协议逆到一半

已确定的事实：

- 设备是 **hid2com 桥**：主机按 `[长度][APDU…]` 写 64 字节 HID 报告，设备把数据转给卡片模块
- 错误回执是明文 ASCII：`no card!(11->0)`、`usb report type error!(0x00)`、`hid2com: xmit drop(N)`
- 对 `00 A4 00 00 02 60 02`（SELECT）等 APDU，即使在卡位上也稳定返回 `no card!(11->0)`
- 空闲时每 15 秒发一次状态帧：`0D 10 0B 00 <计数> 02 … 5A C3 00 04 90 00`

结论：**帧格式已摸清，缺的是"寻卡/上电射频"那条指令**（厂商私有），要么拿厂商 Linux SDK/协议文档，要么用 Windows 演示程序抓一次 USB 包照抄。

复现脚本：`app/tools/id_poll.py`、`app/tools/hid_probe.py`。

### 7.4 MIPI 摄像头（IMX219）：⚠️ 有流但没 V4L2 节点

- `cam-test` 自动探测成功：`detect imx219_spm sensors in csi3: success, 1920x1080@30`
- 但它走 `/dev/cam_sensor2` + `libsdkcam.so` 用户态通道，**内核没有创建 V4L2 采集节点**
- 所以 OpenCV/kiosk 拿不到画面，界面上仍是占位图
- 接入办法：写一个基于 `libsdkcam` 的取帧小服务（C，NV12→JPEG→HTTP），再让 kiosk 拉流；预估 2–3 小时，前提是能拿到 `libsdkcam` 头文件或示例

### 7.5 RFID 读卡器（CH340）：⚠️ 完全静默

- 115200 / 9600 两档、2 秒被动监听 + 4 种常见帧（JSON/AT/AA55/Modbus）均无任何字节
- 说明它要么处于"等待特定轮询指令"模式，要么波特率/接线不符
- 需要型号（读卡器外壳上的牌子）才能对症下药

详见 [05-身份证读卡器接入](05-身份证读卡器接入.md)。

### 8.2 RFID：✅ 已完全打通（真卡读取成功）

从 `RFID读写二次开资料V23B(串口)` 的 C++ 样例 + 使用手册拿到完整协议：

```
读卡号命令： 01 08 A1 20 00 01 00 76
              ↑  ↑  ↑  ↑  ↑        ↑
           包头 长度 命令 地址 参数  校验和(= ~XOR(前7字节))
成功应答：   04 0C 02 20 00 04 00 0A D2 1E 00 17
              ↑  ↑  ↑  ↑  ↑  └卡类型┘ └─ 卡号 ─┘ 校验
            类型 长度 命令 地址 状态
失败应答：   TT 08 CC 20 01 00 00 <校验>
默认：9600 8N1，读写器地址 0x20
```

**实测结果（真卡）**：
- 卡号 `CARD0001`，卡类型 `0400`
- 校验和 `~XOR` 精确匹配
- 应答帧前面偶尔带若干 `0x00` 填充，因此驱动按「长度字节 + 校验和」扫帧，不写死包类型

**已落地**：`app/backend/devices/rfid_serial.py`
- 独立守护线程，每 ~0.6s 发一次读卡命令
- 扫帧 + 校验 + 3 秒去重（同一张卡不重复触发）
- 读到卡 → 审计 + SSE 广播（界面弹出「已识别 房卡 XXXXXXXX」）→ 若当前在「房卡」步骤则自动推进流程

**验证过的完整链路**：
```
选房 8801 → 扫码支付 → 【房卡步骤：真卡 UID CARD0001 自动读入】→ 下发门锁 → 完成页
完成页显示：房间 8801 / 临时开门码 772004 / 房卡 UID CARD0001 / 门锁已授权
```

设备状态栏「房卡读写」已变绿（串口 /dev/ttyUSB0）。

**踩过的坑**：一开始多个波特率都"无应答"，是因为测试脚本读窗口太短 + 串口缓冲区里的回声被当成数据；改成按校验和扫帧、稳定的 0.45s 读窗口后一次成功。

### 8.3 摄像头：✅ 已打通（实时画面进入一体机界面）

`K1边缘视觉实验套件` + `实验手册` 给出了关键信息：**不要用 v4l2src / `VideoCapture(/dev/videoN)` 读 IMX219**——K1 的 MIPI 走 NV12 非连续平面缓冲，必须用 SpaceMiT 的 GStreamer 元件 `spacemitsrc`。

**可用管线**（已写进 `config.py` 的 `camera.pipeline`）：

```
spacemitsrc location=/usr/share/camera_json/csi3_camera_auto.json close-dmabuf=1 !
video/x-raw,format=NV12,width=1920,height=1080 !
videoconvert ! video/x-raw,format=BGR !
appsink drop=true max-buffers=1 sync=false
```

**验证结果**：
- 首帧 1920×1080 采集成功（3.6 秒内），画面内容正常（灰度均值 103，非全黑/纯色）
- 后端持续取流 **9.4 fps**（缩到 640×360 供界面用）
- `/api/camera/snapshot.jpg` 返回 200；`/api/camera/stream` MJPEG 正常推流
- 一体机「人脸」页实时显示画面 + 绿色取景框
- **断电重启后自动恢复**（后端启动即拉流，失败每 10 秒重试）

**前提**：`/usr/share/camera_json/csi3_camera_auto.json` 存在（由 `cam-test` 生成）。
换 CSI 口或换摄像头时先跑一次：

```bash
sudo cam-test /usr/share/camera_json/csi1_camera_detect.json   # CSI1（22pin/4-lane）
sudo cam-test /usr/share/camera_json/csi3_camera_detect.json   # CSI3（15pin/2-lane，当前）
```

**注意**：MIPI 排线不支持热插拔，插拔务必断电。

**遗留**：目前只是"能出画面"，还没做人脸检测/比对——界面上的"人脸核验"是抓拍存档 + 模拟通过。
要真做人脸可加 OpenCV Haar，或复用套件里的 YOLOv8n（需 `python3-spacemit-ort`）。
