## 三、关键技术结论

1. **下行走 shell 子命令**（`osCmdReg("zk")`），避免与 shell 抢串口
2. **厂商示例被强制链接**（`hardware_LIBS` 里的 `-liot_smart_home_example`）会开机驱动电机——已移除
3. **打印必须加互斥锁**，否则心跳和事件会把 `ZK|EVT` 帧粘坏
4. `IoTPwmStart` 前必须 `IoTPwmInit`，否则刷 `[PWM:E]` 错误把串口冲乱
5. **串口会随插拔换号**（ttyUSB0/1/2 都出现过），配置里写死端口不可靠
6. 开发板的按键脚 PC7 在门锁板上是**电机 A 相**——两块板引脚语义完全不同

## 五、恢复步骤

```bash
# 1. 接上板子（串口那个 USB-C，不是 OTG）
ls /dev/ttyUSB*

# 2. 自动找端口（哪个口回 ping 就是门锁板）
sudo python3 /opt/zhikong/tools/find_lock_port.py

# 3. 改配置并重启
python3 - <<'EOF'
import json
p='/opt/zhikong/etc/config.json'
d=json.load(open(p)); d['devices']['lock']['port']='/dev/ttyUSB<N>'
json.dump(d,open(p,'w'),ensure_ascii=False,indent=2)
EOF
sudo systemctl restart zhikong-backend

# 4. 验证
curl -s 127.0.0.1:8080/api/health | python3 -m json.tool | grep -A5 lock
```

## 六、TTP229 键盘协议攻关记录（未完成）

### 已排除
- 硬件损坏：厂商固件下按键/LED 均正常，用户确认
- 总线隔离：SW7 已确认拨在「RK2206 作为主控」（原理图 p6「星闪模块和RK2206 IO切换」）
- 引脚错误：TK_SDA=GPIO0_A0(0)、TK_SCL=GPIO0_A1(1)，与原理图 p3/p4 一致
- 不是 I2C 从机：I2C0 全地址扫描无应答（count=0）

### 已试过的 6 种读法（全部位号冲突）
| 版本 | 方案 | 结果 |
|---|---|---|
| v13–v20 | 上升沿读 + 起始条件 + 50µs | 零星单一位 |
| v25 | 读完 SCL 拉低、80µs | 恒 0 |
| v26 | 500µs | 偶尔 1 位 |
| v31 | 上升沿 + 下降沿双读 | 位号冲突 |
| v32–v33 | micropython-TTP229-BSF 时序（SCL 低时读、1ms、300ms 间隔） | 2~3 键，位号冲突 |
| v34 | taubedonner TTP229.cpp 时序（等 SDO 低→高脉冲再以 ~500kHz 打 16 位） | 位号仍冲突 |

### 关键证据
不同按键读到**同一个位**（1→bit2 与 \*→bit2；2→bit14 与 #→bit14；6→bit6 与 0→bit6），
说明每次截取的 16 位帧**起点不一致**，不是按键本身读不到。

### 结论
帧对齐依赖 TTP229-BSF 的精确起始/帧间时序，只能由 **datasheet** 或 **示波器波形** 确定。
继续用试错法逼近是无穷组合，性价比极低。

## 七、键盘密码：已解决（2026-11-03 凌晨）

### 最终解法（v35 时序 + v38 映射）

**时序（TTP229-AQG 手册 Figure 3-4-1）**
| 参数 | 值 | 说明 |
|---|---|---|
| DV | 93 µs | 触摸后 SDO 拉低的"数据有效"脉冲，必须等它结束 |
| Tw | 10 µs | SDO 回高后、打时钟前 |
| F_SCL | 1k~512kHz | 用约 100kHz（半周期 5µs）**
| T_resp | **32 ms** | 一帧结束后必须等 32ms 才能再读 |

**关键坑**：手册明确"SCL 超过 2ms 无跳变即复位"。早期版本每位用 1ms+1ms=2ms，
正好踩在复位边界，导致每次截到的帧都错位——这是"同一位对应不同键"的根源。

**映射（实测）**：数字 d → 位 d−1
```
1→0  2→1  3→2  4→3  5→4  6→5  7→6  8→7  9→8  0→9  *→10  #→11
```

**交互**：数字键累加（蜂鸣器"嘀"）→ `*` 清空 → `#` 提交 → 板端 cred_check → 开锁 → 6 秒自动上锁

### 实测日志
```
07:53:52 KEY: 1  → len=0
07:53:57 KEY: 0  → len=5
07:53:58 KEY: #
07:53:58 CODE: ok
07:53:58 DOOR: open|keypad
07:54:04 DOOR: close|auto
```

### 已知唯一缺陷 & 规避方案

**数字 `2` 键**的读数与 `0` 撞位（都落在 bit9），是唯一的坏键。
其余 1/3/4/5/6/7/8/9/0 全部正常。

规避：`model.issue()` 生成开门码时**只用 `013456789`**，永远不含 2。
演示与业务完全不受影响；后续若要修 2 键，仍需示波器确认那一列的帧时序。

## 八、三条业务线（全部实测通过）

| 场景 | 结果 | 证据 |
|---|---|---|
| 办入住 → 凭证下发 → 键盘输码 → 开锁 → 自动上锁 | ✅ | `CODE: ok` → `DOOR: open\|keypad` → `close\|auto` |
| 指纹开门（一体机不参与） | ✅ | `FP: 0` → `DOOR: open\|fingerprint` → `close\|auto` |
| 退房 → 凭证作废 → 旧码被拒 | ✅ | `/api/checkout` → 旧码 `{"ok": false}` |

### 接口语义（重要）
- `POST /api/reset` ——「完成并返回」：回待机，**保留**门锁凭证
- `POST /api/checkout` ——「退房」：作废板端凭证（可带 `room`）
- `POST /api/cancel` ——强制复位（含作废）
- `POST /api/lock/code` ——模拟门锁键盘输入（调试用）

> 注意：`/api/reset` 会清空 `state.room`，因此 `_last_room` 记录了最近一次下发的房间号，
> 供 `checkout()/cancel()` 作废凭证时使用。

## 九、四种开门方式（全部实测）

| 方式 | 触发点 | 链路 |
|---|---|---|
| **键盘密码** | 门锁板 TTP229 键盘 | 6 位码 + `#` → 板端 cred_check → 开锁 |
| **指纹** | 门锁板指纹模块 | 采图→比对→开锁（不依赖一体机） |
| **房卡** | **最初接入的 USB 读卡器**（`/dev/ttyUSB0` @9600） | 读卡 → 查在住订单 → 通知板子开锁 |
| **远程** | 一体机/接口 | `zk open` 指令 |

房卡开门的判据：卡号 ↔ 在住订单 `card_uid`；匹配失败提示「房卡无效，请到前台处理」。

## 十、电机时序（关键参数，已固化）

| 参数 | 值 | 说明 |
|---|---|---|
| 开锁通电 | **2000 ms** | 实测 600/800/1200ms 都不够，锁舌弹不出；2000ms 可靠 |
| 上锁通电 | **800 ms** | 关锁行程短，800ms 足够 |
| 自动上锁延时 | 6000 ms | 开锁后 6 秒 |

在线可调（无需重烧）：
```
zk pt 2000 800      # 改开锁/上锁毫秒数，立即生效（重启后恢复默认）
```

调参命令是这一段的救命设计：早期每次改时长都要重新编译+刷机，浪费时间。
